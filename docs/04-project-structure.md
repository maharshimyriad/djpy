# Project Structure

The workspace root is the Django project root (it is named `django` on disk, so we avoid adding a second, unnecessary project directory). It now contains the three apps, models and migrations, views and forms, shared templates, Bootstrap styling, middleware, signals, and tests. The app templates are grouped under the project-level `templates/` folder so they can share one base layout.

The local `.venv/` folder and `db.sqlite3` file are generated during setup and ignored by Git, so they are omitted from the tree. App forms and URL maps exist, but app-local template folders do not: all pages are stored under the shared root `templates/<app>/` folders. `.env.example` lists supported setting names but is not loaded automatically.

## Project-Level Files

| File or directory | Purpose and connections |
| --- | --- |
| `manage.py` | Command-line entry point for this project. It loads the project's settings so commands such as `runserver`, `migrate`, and `test` know which Django project to use. |
| `config/__init__.py` | Marks `config` as a Python package so Python can import it. |
| `config/settings.py` | Project-wide configuration: enabled apps, middleware, templates, database, static files, and authentication defaults. Django and the apps use these settings. |
| `config/middleware.py` | Custom educational middleware that measures request duration and adds a response header only in development. `settings.py` places it in the middleware chain. |
| `config/urls.py` | The root URL map. It sends URL sections to app URL files and connects project-wide pages such as the admin site. |
| `config/asgi.py` | ASGI server entry point for servers that support asynchronous web protocols. It is generated by Django and normally does not need editing for these synchronous pages. |
| `config/wsgi.py` | WSGI server entry point, used by many traditional Python web servers. It is separate from application URL or page logic. |
| `apps/__init__.py` | Makes the apps folder importable as a Python package, allowing app paths such as `apps.projects`. |
| `templates/base.html` | Shared HTML frame for pages, such as navigation, messages, and common CSS/JavaScript. App templates extend it to avoid repeating the whole page layout. |
| `templates/includes/` | Small reusable template fragments shared by multiple pages, such as a navigation or confirmation dialog. |
| `static/` | Project-owned CSS and JavaScript. Templates use Django's static tag; Bootstrap 5.3 and Bootstrap Icons are loaded from their CDNs. |
| `docs/` | Learning notes that explain the architecture and later implementation decisions. |
| `.env.example` | Documents `DJANGO_SECRET_KEY`, `DJANGO_DEBUG`, and `DJANGO_ALLOWED_HOSTS` without containing real values. Django does not read this file automatically. |
| `.gitignore` | Excludes generated or local-only files from version control, including the virtual environment, local database, and secret environment file. |
| `requirements.txt` | Lists Python packages needed to recreate the environment. It currently pins Django 6.1.3. |
| `README.md` | Gives the setup, migration, superuser, server, URL, and troubleshooting instructions for the current phase. We will update it as features are added. |

## Files Inside Each App

The `startapp` command created `admin.py`, `apps.py`, `models.py`, `tests.py`, `views.py`, and `migrations/`. We added `forms.py` and `urls.py` as the application grew. Page templates are project-level so all apps can share `templates/base.html` and common includes.

| App file or directory | Purpose and connections |
| --- | --- |
| `apps/<app>/apps.py` | App configuration, including its import path and readable app name. `settings.py` refers to this configuration through `INSTALLED_APPS`. |
| `apps/<app>/models.py` | Database-backed Python classes. `projects/models.py` defines `Project`; `tasks/models.py` defines `Task`. Django uses their fields and relationships to generate migrations. |
| `apps/<app>/migrations/` | Versioned schema changes. `makemigrations` created the initial project and task migrations; `migrate` applied them to SQLite. |
| `apps/<app>/forms.py` | Defines accepted browser input and validation. Views check forms before saving model changes. |
| `apps/<app>/views.py` | Request-handling functions. App URL patterns call these functions; views coordinate authentication, forms, ORM queries, templates, and responses. |
| `apps/<app>/urls.py` | App-level path patterns connect browser URLs to views; the root `config/urls.py` includes them. |
| `templates/<app>/` | Holds page templates by feature area under the shared root template directory; pages extend `templates/base.html`. |
| `apps/<app>/admin.py` | Registers models with Django's admin site and can configure how they are displayed. |
| `apps/<app>/tests.py` | Automated checks for models, forms, views, authentication, and ownership rules. The project test command discovers these tests. |
| `apps/tasks/signals.py` | Registers the Task `post_save` receiver imported by `TasksConfig.ready()`. |
| `apps/<app>/__init__.py` | Marks the app as a Python package. |

The `accounts` app uses Django's built-in `User` model rather than defining a separate user model. Its forms and views connect registration and authentication pages to Django's built-in authentication system.

## Why Keep Three Apps?

The app boundaries match the concepts we want to learn: account access, project ownership, and task management. Keeping these responsibilities separate makes it easier to find code without adding extra layers or abstractions. The apps still cooperate: a task belongs to a project, and the project's owner determines who may access that task.
